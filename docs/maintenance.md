# 유지보수와 운영

## 공개 주소와 개인 기록

이번 변경은 주소 이전을 수행하지 않는다. 기존 URL, 탭 경로, 할 일 ID, `rs-check:*`, `rs-check-once`, `rs-done-days`, RS1 백업 형식을 유지한다. 이름 변경을 이유로 기존 ID를 바꾸거나 재사용하지 않는다. 종료 자료를 삭제하면 과거 날짜의 계산에 영향을 줄 수 있으므로 관리 화면의 상태 필터로 정리한다.

## 코드의 책임

| 위치 | 책임 |
|---|---|
| `shared/validation.js` | 브라우저·관리 서버·빌드가 함께 쓰는 자료 형식, 실제 날짜와 시간 검사 |
| `shared/runtime.js` | 요청 제한시간, 동시 요청 합치기, 재시도 대기, 마지막 정상 자료 보관 |
| `shared/records.js` | 기존 RS1 기록 검증과 합치기, 부분 복원 실패 시 원상 복구 |
| `shared/schedule.js` | DOM과 무관한 일정 비교와 관리자 병합·분리 규칙 |
| `src/05-resources.js` | 자료 클라이언트와 기존 화면 상태 연결 |
| `src/`의 나머지 화면 파일 | 기존 UI, 탭과 모바일 앱 연결 |
| `styles/` | 순서가 명시된 편집용 CSS 원본 |
| `app.js`, `style.css`, 탭별 HTML, `sample-data.js` | 생성 결과. 직접 편집하지 않음 |

기존 화면 전체를 새 프레임워크로 바꾸지 않고, 공통 기능부터 독립 모듈로 분리했다. 화면 파일의 결합 빌드는 기존 설치 앱 호환성을 위해 유지한다. `styles/order.json` 순서를 바꾸면 기존 CSS 우선순위도 달라지므로 변경 전후 화면을 확인한다.

## 자료 작성

- 할 일의 `아이디`는 체크 기록의 키다. 이미 공개한 ID는 변경하지 않는다.
- 투표 종류의 `아이디`는 고정하고 표시 이름만 고친다. 할 일은 `투표종류ID`로 연결한다. 기존 이름 열은 이전 자료 호환용이다.
- 제목과 수량을 분리한다. `수량`, `단위`, `참여 주기`를 입력하고 제목에 수량을 중복 기입하지 않는다.
- 시작·종료일을 모두 비우면 기간 미정이다. 잘못된 날짜를 임시 값으로 넣지 않는다.
- `확인일`, `적용기준`, `원문링크`는 실제로 확인한 근거만 입력한다. 빈 값은 미확인 상태이며 배포 시 자동으로 현재 날짜를 넣지 않는다.
- 음방 기본 정보의 사전투표·실시간 투표·결방 입력은 관리 화면에서 묶어 제공한다.
- `일정보정.csv`의 `보정`은 원본을 손대지 않고 제목·링크·종료일을 덮어쓴다. `병합`·`분리`는 대상 ID와 상대 ID의 자동 판정을 명시적으로 제어한다.
- 기간이 끝난 항목도 과거 기록을 위해 보존한다. 진행·예정·미정·종료·수정 항목 필터로 관리한다.

## 관리자 저장 흐름

1. 수정 내용은 기기에도 임시 보관한다. 원본 SHA가 같을 때 복원할 수 있다. 원본이 달라지면 덮어쓰지 않고 JSON으로 내려받을 수 있다.
2. `변경 내용 확인`으로 변경 전후를 확인한다.
3. 공통 형식 검사를 통과하면 서버는 `admin-drafts/<UUID>` 브랜치에 자료와 `.admin/transaction.json`을 저장한다. 이 단계에서 `main`은 바뀌지 않는다.
4. `관리자 저장` 작업이 최신 `main`의 원본 SHA를 다시 확인하고, 임시 작업 폴더에서 전체 자료·생성 파일·회귀 테스트·화면 검사를 수행한다.
5. 검사가 통과하면 fast-forward 가능한 경우에만 공개 브랜치로 반영한다. 동시에 다른 자료가 바뀌면 최신 코드 위에서 다시 검사한다. 같은 파일이 바뀌었으면 중단한다.
6. GitHub Pages와 Cloudflare 운영 사이트의 실제 버전을 확인한다. 그 후 받은 공지의 처리 상태를 확정한다.

검사·충돌·배포 실패 시 초안은 남긴다. 배포 실패만으로 정상 원본이나 다른 사람의 후속 편집을 자동으로 되돌리지 않는다. 이미 공개 자료에 반영됐지만 배포 확인에 실패한 요청은 같은 초안으로 재시도할 수 있다.

초안 브랜치는 자동 삭제하지 않는다. 오래된 초안을 정리할 때는 해당 요청이 반영됐는지 먼저 확인한다. 재배포할 원본 SHA와 배포 결과가 작업 로그에 남는다.

## 배포 연결

기존 관리자 Worker에는 `GH_TOKEN`, `ADMIN_PASSWORD`, `SIGN_KEY` 비밀값이 필요하다. `GH_TOKEN`은 해당 저장소 Contents 쓰기와 Actions 쓰기 권한이 필요하다. 비밀값은 저장소에 기록하지 않는다.

GitHub Actions Secrets에는 아래 연결이 필요하다.

| 이름 | 목적 |
|---|---|
| `CLOUDFLARE_API_TOKEN` | 기존 `rescene-admin` Worker와 `rescenefan` Pages의 배포 권한 |
| `CLOUDFLARE_ACCOUNT_ID` | 두 서비스가 속한 Cloudflare 계정 ID |

`Cloudflare 미러 동기화`는 기존 Pages 미러를 업데이트하고, 관리자 Worker는 해당 소스 변경 또는 명시적인 수동 실행 시에만 별도 배포한다. 새 프로젝트나 새 주소를 만들지 않고 Worker의 기존 비밀값도 재작성하지 않는다.

연결 설정을 바꾸면 Actions에서 배포 권한을 다시 확인한다. 새 관리자 화면은 저장 서버 프로토콜 2를 확인하므로, 서버가 구버전이면 저장 요청을 보내지 않고 기기 초안을 보관한다. 이를 통해 새 저장 흐름을 구버전 서버의 즉시 공개 방식으로 잘못 실행하지 않는다.

검증된 전체 적용 순서: 연결 설정 → PR 검증 → 병합 → GitHub Pages 정식 반영 → Cloudflare Pages 미러 확인 → 관리자 저장·공지 완료·실제 화면 확인. 관리자 Worker는 관련 코드 변경 시 별도 배포한다. 연결이 없는 상태에서는 코드 준비 완료와 운영 적용 완료를 구분해서 보고한다.

## 점검 명령

```sh
node --test tests/*.test.mjs
python -m unittest discover -s tests -p 'test_*.py'
node tools/validate_data.mjs
python tools/build_style.py --check
python tools/build_js.py --check
python tools/check_structure.py
```

자료·화면 생성은 `python tools/prepare_release.py`로 수행한다. 이 명령 자체는 커밋·push·배포하지 않는다. 화면 검사는 기존 `tools/check_site.mjs`를 사용하며 CI에서 모바일·데스크톱 및 라이트·다크를 확인한다.

테스트는 외부 사이트의 실제 투표 규칙이 최신임을 보증하지 않는다. 수집 성공·자료가 실제로 바뀐 시각·운영 배포 완료·원문 확인일은 각각 다른 의미다.

## GitHub Pages 정식 사이트와 Cloudflare 미러 (2026-11-08)

- **대표 사이트:** `https://woniwoniwoniwoni.github.io/todo/` (기존 canonical, sitemap, SEO 등록·개인 체크 기록을 유지)
- **보조 미러:** `https://rescenefan.pages.dev/` (동일한 공개 HTML·CSS·JS·자료를 복제)
- **저장소:** `WONIWONIWONIWONI/todo`의 `main` 하나가 사이트 코드 및 자료의 원본.
- **관리자 API:** 기존 `rescene-admin` Worker. 그대로 유지한다.
- **GitHub 루트 저장소:** `woniwoniwoniwoni.github.io`는 루트 주소를 `/todo/`로 안내한다.

**코드·자료 수정 및 배포:** GitHub Pages를 메인으로 유지하며, Cloudflare Pages는 GitHub Actions가 미러로 배포한다. 관리자의 저장 흐름에서는 GitHub Pages 실제 반영을 확인한 후 Cloudflare **Pages만** 동기화한다. 관리자 Worker는 `admin-worker/**` 또는 `shared/validation.js`가 바뀐 일반 push 혹은 명시적인 수동 배포 때만 재배포한다.

**수집기 커밋 주의:** GitHub Actions 기본 토큰으로 수집기가 `main`에 남긴 커밋은 별도의 push 워크플로를 재실행하지 않을 수 있다. 따라서 3시간 간격 예약 미러 동기화가 누락된 변경을 보완한다. 미러에 이미 같은 커밋의 `mirror-revision.txt`가 있다면 업로드를 생략해 불필요한 Cloudflare Pages 배포 횟수를 줄인다. 3시간은 최대 대기 목표치이며 GitHub의 예약 지연이나 배포 실패가 있으면 더 늦어질 수 있다. 즉시 동기화하려면 **Cloudflare 미러 동기화 → Run workflow**를 실행한다.

**검증:** 미러 배포 후 앱 버전 외에도 주요 공개 JSON, ICS, `sample-data.js`, 배포 커밋을 검증한다. 메인은 다른 주소이므로 검증 전후의 캐시 차이를 고려한다. 두 사이트의 localStorage는 공유되지 않으므로 체크 기록 자동 동기화를 약속하지 않는다. 주소 변경·강제 리다이렉트·기존 검색 등록 삭제는 하지 않는다.

**AI 협업**은 [공용 작업지시서](AI_SHARED_WORK_INSTRUCTIONS.md)의 인수 절차와 미해결 표를 따른다.

**메인 우선 게시 보장:** X 공지 수집기가 `data/inbox.json`을 바꾸면 `x-inbox.yml`에서 GitHub Pages 빌드를 명시적으로 요청한다. 미러 신규 업로드에 앞서 메인 사이트의 주요 JSON/ICS 파일이 체크아웃한 배포본과 일치하는지 확인한다. 단 X 공지는 관리자 승인 전까지 공개 할 일로 자동 등록되지 않는다.
